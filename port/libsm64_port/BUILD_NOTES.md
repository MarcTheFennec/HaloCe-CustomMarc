# Build notes

The exact commands, in order, with what each produced here and what could not
be run. Everything in `port/libsm64_port` and `port/third_party/libsm64` is
built by these commands and nothing else.

## The machine

Linux, x86-64, Python 3.11, `cc` (gcc) as the host compiler, `ninja` on PATH.
No `apt` (the mirrors are unreachable, so nothing could be installed), no
`clang`, no 32-bit glibc development files, no 32-bit SDL3, and no
`raw.githubusercontent.com`.

Two consequences, both worked around and both recorded in `TEST_RESULTS.md`:

- **The game executable cannot be linked here.** `ninja linux` needs
  `clang -m32`, 32-bit glibc and 32-bit SDL3. What ran instead: every unit of
  the module compiled *through the port's own ninja rules and flags*, with a
  clang that targets 32-bit x86 (see "Verifying without a linker" below).
- **libsm64's build fetches Mario's geometry from the network.** Worked around
  with `tools/offline_import_geo.py`, which performs the same rewriting from a
  local copy of the two files.

## 1. Getting the sources

```
git clone https://github.com/MarcTheFennec/HaloCe-CustomMarc        # this repository
git clone https://github.com/libsm64/libsm64                        # fd11813
```

libsm64 was then vendored, minus its build outputs (which this repository must
not hold):

```
cp -r libsm64 port/third_party/libsm64      # without .git, build/, dist/,
                                            # test/level.c and test/level.h
```

`port/third_party/libsm64/PORT_NOTES.md` records what it is and what is
deliberately missing from it.

## 2. Building libsm64

One command, with or without the network:

```
python3 port/libsm64_port/tools/build_libsm64.py --out /tmp/libsm64.so --jobs 8
```

It imports Mario's geometry (fetching a cache of the two files it needs into
`~/.cache/halo-sm64-port/mario-geo` the first time, or using the one named by
`HALO_SM64_GEO_CACHE`/`--cache`), then builds the vendored source with
libsm64's own Makefile, or — where there is no `make`, as on a Windows
runner — by compiling the same sources with the same flags itself
(`--no-make` forces that path).

```
offline_import_geo: writing /home/.../.cache/halo-sm64-port/mario-geo
offline_import: wrote .../port/third_party/libsm64/src/decomp/mario
build_libsm64: make -C port/third_party/libsm64 lib LDFLAGS=-Wl,--no-as-needed -lm -shared -j8
build_libsm64: /tmp/libsm64.so
```

The port's build does this for you, with the ABI the game needs: the game is
32-bit, so the library it opens has to be too.

```
ninja build/linux/libsm64.so     # --target=i686-linux-gnu -m32
ninja build/windows/sm64.dll     # --target=i686-pc-windows-msvc
```

In CI that is part of the build: `tools/ci_build.py linux debug
--enable-libsm64` compiles the game with the module, links it, builds the
library beside the executable, and (Linux) runs the module's tests against a
libsm64 built for the runner. Android is refused: its guest has no dynamic
loader.

Two traps, both handled by the tool:

- **`-lm` must stay in `LDFLAGS`.** libsm64 links with `$(CC) $(LDFLAGS)` and
  uses `sqrtf`; without `-lm` the shared library has an undefined symbol and
  `dlopen` fails at run time. The tool's default `LDFLAGS` is
  `-Wl,--no-as-needed -lm -shared`.
- **`make` says "nothing to be done"** while `dist/libsm64.so` exists, even
  after a source change: delete it first. `build_libsm64.py` always invokes
  `make`, which is idempotent for the objects and re-links the library.

Mario's geometry (`src/decomp/mario/geo.inc.c`, `model.inc.c`) is generated by
that step. It is gitignored
(`port/third_party/libsm64/src/decomp/mario/`) and is **not** committed: it is
derived from Nintendo's game.

## 3. Configuring the port

```
python3 configure.py                    # the module is not built (the default)
python3 configure.py --enable-libsm64   # it is
```

`--enable-libsm64` makes every unit see `-DHALO_CE_ENABLE_LIBSM64=1`, adds the
module's two units to the Linux (and, on a Windows host, Windows) build, and
adds a rule that builds `build/linux/libsm64.so` beside the executable. The
arguments are recorded in `build.ninja`, so reconfiguring keeps it.

## 4. Building

```
ninja linux        # build/linux/halo       (needs clang -m32, 32-bit SDL3)
ninja windows      # build/windows/halo.exe (on a Windows host)
ninja android      # the APK                (the module is not built there)
```

Only these two units of the build are new:

```
build/linux/libsm64_port/libsm64_port_sm64_port_core.o
build/linux/libsm64_port/libsm64_port_sm64_port_halo.o
build/linux/libsm64.so                 # opened at run time, not linked
```

## 5. Verifying without a linker

This sandbox has no 32-bit clang, but the port's rules will take any compiler
through `--linux-cc`, and a compiler that targets 32-bit x86 is enough to
compile a unit (only *linking* needs the 32-bit libraries and SDL3). A
32-bit-capable clang was installed from PyPI and wrapped so that the flags the
port passes reach it in a spelling it accepts:

```
pip install ziglang                     # a clang toolchain, no root needed
cat > /tmp/zig-linux-cc.sh <<'EOF'
#!/bin/bash
args=()
for a in "$@"; do
  case "$a" in
    --target=*) args+=(-target x86-linux-musl) ;;   # 32-bit x86, like -m32
    -m32) ;;
    *) args+=("$a") ;;
  esac
done
exec zig cc "${args[@]}"
EOF
chmod +x /tmp/zig-linux-cc.sh

python3 configure.py --enable-libsm64 --linux-cc /tmp/zig-linux-cc.sh
ninja build/linux/libsm64_port/libsm64_port_sm64_port_core.o \
      build/linux/libsm64_port/libsm64_port_sm64_port_halo.o
```

```
[1/2] LINUX CC build/linux/libsm64_port/libsm64_port_sm64_port_halo.o
[2/2] LINUX CC build/linux/libsm64_port/libsm64_port_sm64_port_core.o
```

The same trick compiles any other unit of the game:

```
ninja build/linux/obj/game/player_control.o
```

Three real bugs came out of compiling in this configuration that the host
build could never have shown:

1. `log` is a macro in `port/include/halo_math.h`, which the game's prefix
   header includes, so the host callback had to be renamed `log_message`.
2. The module needs the game's *full* include path, not the platform layer's
   two directories: `data.h` includes `tag_files.h` by bare name.
3. The include directories that hold a space (`source/saved films`) have to be
   quoted the way `linux_build.py` quotes them.

## 6. The tests

```
cd port/libsm64_port/tests
make                       # build and run against a real libsm64 if there is one
make test                  # against the ROM-free test double
make test-real             # against $(LIBSM64_DIST)/libsm64.so (default ../../../build/linux)
make test_abi && ./test_abi
make check-header          # diff the vendored libsm64.h against tests/libsm64.h
make clean
```

No Halo source, no game build, no ROM: plain C99 and a C compiler.
`SM64_PORT_TEST_LIBRARY=/path/to/libsm64.so ./test_sm64_port` runs the same
binary against any build of libsm64.

## 7. Running it

Put your own US SM64 ROM where the module can find it and turn it on:

```toml
# config.toml (written with the defaults the first time the game runs)
sm64.enable = true
sm64.rom = "/home/you/baserom.us.z64"
```

then, in the console (`~`):

```
sm64_status          # did it start? (it says why not, if not)
sm64_spawn           # an actor in front of the player
sm64_debug 1         # draw him
sm64_show_collision 1
```

`BUILD_NOTES` for the ROM: it is read once, at start-up, through libsm64, and
never copied anywhere. Nothing in this repository contains it, or any part of
it.
